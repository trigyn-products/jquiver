# REST and HTTP Integration

## Purpose

Explain how JQuiver server-side scripts invoke internal or external HTTP APIs through the platform REST XML contract and `ScriptUtil` wrapper.

## When to use this file

Use this file when:

- a Dynamic REST JavaScript or another server-side script calls an HTTP endpoint;
- an AI agent must generate XML for `jq_executeRESTCall`;
- headers, query parameters, raw bodies, key-value bodies, authentication, SSL verification, timeouts, or file attachments must be configured;
- an existing REST XML payload must be reviewed or troubleshot.

## Verified source behaviour

The platform script template exposes:

```javascript
function jq_executeRESTCall(a_strRestXML) {
    return jq_scriptUtilObject.executeRESTCall(a_strRestXML);
}
```

The Java utility exposes:

```java
public final Object executeRESTCall(String a_strRestXML)
    throws CustomStopException
```

Verified processing behaviour:

1. blank XML causes `RuntimeException("Rest XML has not been provided")`;
2. the XML is passed to `jwsDynamicRestDetailService.executeRestXML(a_strRestXML)`;
3. the resulting `CustomResponseEntity` is returned to the script;
4. `CustomStopException` is logged and propagated;
5. the source comment says internal API URLs should use `JAPI` as the prefix instead of `API`.

The wrapper and Java method do not themselves document every XML field. The supplied XML contract is therefore the source for field intent, while parser-specific validation and conversion rules must be verified from the REST XML implementation or a working runtime.

## Conceptual flow

```text
Business or integration trigger
    -> server-side JavaScript
    -> jq_executeRESTCall(restXML)
    -> ScriptUtil.executeRESTCall(restXML)
    -> executeRestXML(restXML)
    -> internal or external HTTP endpoint
    -> CustomResponseEntity returned to the script
```

## XML capabilities

The supplied `<rest>` contract can describe:

- SSL-certificate verification;
- target URL;
- HTTP method;
- request content type;
- timeout;
- request headers;
- query parameters;
- raw or key-value request bodies;
- parameters intended to become JSON structures;
- internal JQuiver authentication selection through the special `at` header;
- attachments from an internal upload, filesystem path, or the current call.

Read the exact hierarchy, allowed documentation values, and limitations in:

```text
../reference/jquiver-rest-xml-reference.md
```

## Calling pattern

```javascript
var restXML = `
<rest>
    <verifySSL>true</verifySSL>
    <url>https://api.example.com/v1/items</url>
    <type>GET</type>
    <content-type>application/json</content-type>
    <timeout>30000</timeout>
    <request>
        <query-param>
            <parameter>
                <name>status</name>
                <value>ACTIVE</value>
            </parameter>
        </query-param>
    </request>
</rest>`;

var response = jq_executeRESTCall(restXML);
```

The timeout unit in the supplied XML is not stated. Do not assume that `30000` means milliseconds until the parser or a working example confirms it.

## Internal API URLs

The Java source includes this instruction:

```text
For Internal API calls, URL should be prefix with JAPI not API
```

Preserve this rule when generating internal-call examples, but verify the exact accepted URL format in the target JQuiver version. Do not invent a production endpoint path.

## Authentication selector

The supplied XML describes a special request header named `at`.

Documented values are:

| Value | Intended authentication mode |
|---|---|
| `7d1oa821` | OAuth |
| `7d1dba821` | Database authentication |
| `7d1ldap821` | LDAP authentication |

Example:

```xml
<headers>
    <parameter>
        <name>at</name>
        <value>7d1oa821</value>
    </parameter>
</headers>
```

This appears to select platform token handling when authentication is enabled and a bearer token is passed or generated by the application. Exact token lookup, injection, refresh, and failure behaviour must be verified from the authentication and REST XML processing source.

Do not place an actual bearer token, client secret, password, session cookie, or API key in documentation.

## Body modes

### Key-value mode

Use `contentType="keyValue"` or omit the attribute when the parser should process individual `<parameter>` nodes according to the HTTP method and content type.

```xml
<body contentType="keyValue">
    <parameter>
        <name>name</name>
        <value>Sample Item</value>
    </parameter>
</body>
```

### Raw-body mode

Use `contentType="rawBody"` when the body value must be sent directly.

```xml
<body contentType="rawBody">
    <parameter>
        <name>data-raw</name>
        <value><![CDATA[{"name":"Sample Item"}]]></value>
    </parameter>
</body>
```

Rules from the supplied contract:

- `data-raw` is mandatory in raw-body mode;
- other child elements are ignored in raw-body mode;
- raw-body mode does not support file attachment.

Use CDATA when raw content contains XML-sensitive characters.

### JSON-typed parameter

```xml
<parameter dataType="json">
    <name>profile</name>
    <value><![CDATA[{"department":"Technology"}]]></value>
</parameter>
```

The contract says this creates a JSON object from the supplied key and value. Verify the exact accepted value syntax, nesting, array behaviour, invalid-JSON response, and interaction with `<content-type>`.

## Attachments

The supplied contract documents:

| Type | Intended source |
|---|---|
| `1` | Internal uploaded file; `<path>` contains a file-upload ID |
| `2` | Server filesystem; `<path>` contains an absolute path |
| `3` | File uploaded in the current call; exact binding requires verification |

Do not use attachments with `contentType="rawBody"`.

Do not allow untrusted input to select arbitrary server paths or upload IDs. Verify access control, size limits, MIME handling, filename sanitisation, temporary-file cleanup, and type `3` request binding.

## SSL verification

`<verifySSL>` is optional and defaults to `true` according to the supplied XML.

Keep it enabled for normal use:

```xml
<verifySSL>true</verifySSL>
```

Disabling certificate verification can expose credentials and data to interception. Use `false` only under explicit, controlled, non-production or approved compatibility requirements.

## Response handling

The Java method returns a `CustomResponseEntity` as an `Object` to JavaScript.

Do not assume property names such as `status`, `body`, `headers`, or `statusCode` until the target runtime response object has been inspected or the class and script-engine conversion are verified.

Recommended pattern:

```javascript
var response = jq_executeRESTCall(restXML);

if (response === null || response === undefined) {
    throw new Error("REST call returned no response");
}

// TODO: Verify the actual response properties before reading them.
```

Avoid logging full response bodies when they may contain credentials, personal data, tokens, or confidential business data.

## Safety and reliability rules

- Treat every REST call as potentially side-effecting.
- Validate or allow-list target hosts; prevent server-side request forgery.
- Do not allow user input to control protocols, hosts, ports, internal addresses, or unrestricted paths.
- Use HTTPS and keep SSL verification enabled.
- Store secrets outside XML and source control.
- Use explicit timeouts once the required unit is verified.
- Limit request and response sizes.
- Restrict redirects or verify the final host if redirects are supported.
- Sanitize logs and error messages.
- Review retry behaviour before calling non-idempotent endpoints.
- Validate attachment source, ownership, size, and type.
- Never execute generated examples during documentation or analysis work.

## Troubleshooting

### `Rest XML has not been provided`

Cause:

- `null`, empty, or blank XML was supplied.

Fix:

- construct the XML before calling `jq_executeRESTCall`;
- verify the intended variable is passed;
- avoid logging secrets while checking whether the XML exists.

### XML parsing failure

Check:

- closing tags;
- escaped ampersands and angle brackets;
- CDATA around raw JSON/XML/text;
- one actual value instead of documentation alternatives such as `rawBody | keyValue`;
- correct case for `contentType` and `dataType` attributes;
- required `<url>` and `<type>` values.

### Authentication failure

Check:

- authentication is enabled in the target instance;
- the `at` header name is correct;
- one documented selector value is used;
- the relevant OAuth, database, or LDAP configuration exists;
- token generation or token forwarding is actually supported for the call;
- logs do not expose tokens.

### File upload or attachment failure

Check:

- attachment type;
- type `1` upload ID;
- type `2` absolute path and server permission;
- type `3` binding in the current request;
- raw-body mode is not used;
- file size and MIME restrictions.

## Known unknowns

The following require parser-source or runtime verification:

- supported HTTP methods and case sensitivity;
- timeout unit and default;
- behaviour when `<content-type>` is omitted;
- exact key-value encoding for each method and content type;
- duplicate header/query/body parameter handling;
- null, empty, repeated, nested, array, numeric, and boolean values;
- exact `dataType="json"` conversion;
- authentication-selector implementation;
- response object properties exposed to JavaScript;
- redirect, proxy, cookie, compression, and retry behaviour;
- SSL trust-store behaviour when `verifySSL` is true;
- attachment multipart field names and `hasEmbeddedImage` relevance;
- type `3` attachment binding;
- maximum payload, response, timeout, and file sizes.

## AI-agent completion criteria

A generated REST integration is incomplete unless it includes, where applicable:

1. verified target URL or internal `JAPI` path;
2. verified method;
3. SSL decision;
4. timeout and verified unit;
5. headers and authentication source;
6. query parameters;
7. body mode and content type;
8. XML escaping or CDATA handling;
9. attachment validation;
10. response-object verification;
11. failure handling and safe logging;
12. side-effect, SSRF, secret, and privacy review.
